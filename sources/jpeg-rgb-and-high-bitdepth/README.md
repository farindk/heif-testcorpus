# jpeg-rgb-and-high-bitdepth

Generated JPEG images in forms that the common encoders do not write: coded
as RGB without colour transform, with 12 bits per sample, and lossless with
16 bits per sample. ISO/IEC 23008-12 Annex H allows all of them, it only
requires a `jpeg` item to conform to ISO/IEC 10918-1.

| | |
|---|---|
| Origin | Generated by `build.py`, no third-party material |
| Files | 9 images with one raw reference file each, 1.3 MB |
| Licence | MIT, as the scripts of this repository (see `LICENSE`) |

## Files

All pictures are 256x128 and full range.

| File | Bit depth | JPEG process | Components | `colr` |
|---|---|---|---|---|
| `jpeg-8bit-444-rgb.heif` | 8 | extended sequential DCT | R, G, B | 1/13/0 |
| `jpeg-8bit-444-rgb-nocolr.heif` | 8 | extended sequential DCT | R, G, B | none |
| `jpeg-12bit-400.heif` | 12 | extended sequential DCT | Y | 1/13/6 |
| `jpeg-12bit-420.heif` | 12 | extended sequential DCT | Y, Cb, Cr 4:2:0 | 1/13/6 |
| `jpeg-12bit-422.heif` | 12 | extended sequential DCT | Y, Cb, Cr 4:2:2 | 1/13/6 |
| `jpeg-12bit-444.heif` | 12 | extended sequential DCT | Y, Cb, Cr 4:4:4 | 1/13/6 |
| `jpeg-12bit-444-rgb.heif` | 12 | extended sequential DCT | R, G, B | 1/13/0 |
| `jpeg-16bit-lossless-400.heif` | 16 | lossless | Y | 1/13/6 |
| `jpeg-16bit-lossless-444-rgb.heif` | 16 | lossless | R, G, B | 1/13/0 |

The `colr` column lists colour primaries, transfer characteristics and
matrix coefficients of the `nclx` colour information.

The two 8 bit files contain the same JPEG. JPEG has no colour signalling of
its own beyond the markers described below, so in the file without `colr` a
reader has to find out from the JPEG that the components are RGB.

## Picture content

The colour gradient of `corpuslib/testpicture.py`, the same as in
`avc-high-bitdepth`. The lossless files hold it sample by sample. In the DCT
based files every 8x8 block of a component is flat, so the picture is a
mosaic. With 4:2:0 and 4:2:2 a chroma block covers two luma blocks in the
subsampled directions.

## Coding

- **DCT based files**: only the DC coefficient of every block is coded, and
  all quantizer values are 1. The DC coefficient of a flat block with the
  value v is 8 * (v - 2^(P-1)), so the inverse DCT returns v without any
  rounding. The decoded samples do not depend on the DCT implementation of
  the decoder.
- **Lossless files**: predictor 1 (the sample to the left), no point
  transform.
- **RGB**: the components have the identifiers 'R', 'G', 'B' and the file
  has an Adobe APP14 marker with colour transform 0. Both mark the
  components as RGB; decoders differ in which of the two they look at.
- The YCbCr and the greyscale files have the component identifiers 1, 2, 3
  and no APP marker.
- The Huffman tables are as simple as possible and not chosen for
  compression.

## Container

One `jpeg` image item with the properties `ispe`, `colr` (except for the
`nocolr` file) and `pixi`. The brands are `mif1` and `jpeg`. There is no
`jpgC` property, the item holds the complete JPEG.

## Reference files

`<name>.<pixel format>.raw` holds the expected decoded planes without any
header, every plane in its own resolution. The 8 bit files have one byte per
sample, the others 16 bit little endian samples that hold the values as they
are coded, for 12 bits in the range 0 to 4095.

The planes of the RGB files are stored in the order G, B, R. This is the
order of the planar GBR pixel formats and of an image with matrix
coefficients 0, where G, B, R take the places of Y, Cb, Cr. The JPEG itself
codes the components in the order R, G, B.

A decoder under test has to reproduce the reference exactly. With libheif,
decode with `heif_colorspace_undefined` and `heif_chroma_undefined` and set
`output_image_nclx_profile_passthrough` in the decoding options.

## Notes for decoders

Observed on 2026-09-29 with FFmpeg 6.1.1, libjpeg-turbo 2.1.5 and the master
branch of libheif.

- FFmpeg returns the 12 bit files in 16 bit pixel formats with the samples
  shifted left by 4 and the coded depth in `bits_per_raw_sample`.
- FFmpeg returns `jpeg-12bit-444-rgb` as `gbrp16le`, but with the planes in
  the order R, G, B. It reorders the planes for the 8 bit format `gbrp` only.
  The FFmpeg 7.1.1 source has the same code.
- FFmpeg returns `jpeg-16bit-lossless-444-rgb` as packed `bgr48le`.
- libjpeg-turbo before version 3 decodes 8 bits only, unless it was built
  for 12 bits, and has no lossless mode.
- libheif with its FFmpeg decoder plugin decodes seven of the nine files. It
  rejects `jpeg-12bit-444-rgb` and `jpeg-16bit-lossless-444-rgb` because of
  their pixel formats. `jpeg-8bit-444-rgb-nocolr` needs the commit "FFmpeg
  decoder: signal the identity matrix for planar GBR from JPEG"; without it
  the picture is decoded with wrong colours.
- libheif with its libjpeg decoder plugin rejects all nine files: the 12 bit
  and the lossless ones because of libjpeg-turbo 2.1.5, the 8 bit RGB ones
  with "Unsupported color conversion request".

## Verification

Performed on 2026-09-29 for the pinned outputs:

- libjpeg-turbo 3.1.4, decoding without colour conversion and with
  replicating chroma upsampling, returns exactly the reference samples for
  all nine files and reports the precision listed above.
- FFmpeg 6.1.1 decodes the JPEG of every file to exactly the reference
  samples, after the shift and the plane order described above are taken
  into account.
- libheif with its FFmpeg decoder plugin decodes the seven files it supports
  to exactly the reference planes, under AddressSanitizer and
  UndefinedBehaviorSanitizer.
- MP4Box and `heif-info -d` parse the container without complaints.
